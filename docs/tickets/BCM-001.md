## Mô tả

Dựng project firmware cho Blue Pill **từ con số không** bằng CMake + Ninja + arm-none-eabi-gcc. Kết quả cuối cùng là một LED nhấp nháy — nhưng thứ thực sự được đánh giá là bạn hiểu từng byte trong file `.elf` từ đâu ra, và MCU đi từ lúc cấp điện tới dòng đầu tiên của `main()` như thế nào.

Đây là ticket duy nhất trong cả dự án mà "LED sáng" gần như không có giá trị. CubeIDE làm được điều đó trong 3 phút. Giá trị nằm ở linker script, startup code và câu trả lời cho phần câu hỏi review.

  - CMSIS-Core: repo `ARM-software/CMSIS_6` (hoặc `CMSIS_5`) trên GitHub
  - Device header: repo `STMicroelectronics/cmsis_device_f1` trên GitHub
- ✅ Chuẩn C11, không extension: `-std=c11`
- ✅ `-Wall -Wextra -Werror` — zero warning

## Yêu cầu kỹ thuật

### 1. Toolchain file — `cmake/arm-none-eabi.cmake`

- `CMAKE_SYSTEM_NAME` = `Generic`, `CMAKE_SYSTEM_PROCESSOR` = `arm`
- Chỉ định `arm-none-eabi-gcc`, `arm-none-eabi-g++`, `arm-none-eabi-objcopy`, `arm-none-eabi-size`
- Xử lý bước kiểm tra compiler của CMake (xem mục *Bẫy thường gặp*)

### 2. Compile & link flags

| Nhóm | Cờ bắt buộc |
|---|---|
| CPU | `-mcpu=cortex-m3 -mthumb` |
| Chuẩn | `-std=c11` (qua `CMAKE_C_STANDARD`, không hardcode) |
| Warning | `-Wall -Wextra -Werror` |
| Section | `-ffunction-sections -fdata-sections` |
| Debug build | `-Og -g3` |
| Link | `-Wl,--gc-sections`, `-Wl,-Map=...`, `-Wl,--print-memory-usage` |
| Runtime | `--specs=nano.specs --specs=nosys.specs` |

### 3. Linker script — `stm32f103c8.ld`

- `MEMORY`: FLASH 64K tại `0x08000000`, RAM 20K tại `0x20000000`
- Section theo thứ tự: `.isr_vector` (đầu FLASH) → `.text` → `.rodata` → `.data` → `.bss`
- `.data` phải có **VMA ở RAM, LMA ở FLASH**
- Export symbol cho startup dùng: `_sidata`, `_sdata`, `_edata`, `_sbss`, `_ebss`, `_estack`
- `_estack` = đỉnh RAM
- Có `ASSERT` đảm bảo còn chỗ tối thiểu cho stack (tự chọn con số, ghi lý do vào docs)

### 4. Startup — `startup_stm32f103.c`

- Vector table là một mảng, đặt vào section `.isr_vector`
- Phần tử đầu tiên là `_estack`, phần tử thứ hai là `Reset_Handler`
- Đủ 16 exception lõi Cortex-M3 **và** toàn bộ IRQ ngoại vi của dòng **medium-density** — tra bảng vector trong RM0008, đừng đoán số lượng
- Mọi handler chưa dùng trỏ về `Default_Handler` qua `__attribute__((weak, alias(...)))`
- `Reset_Handler` làm đúng bốn việc, đúng thứ tự:
  1. Copy `.data` từ FLASH sang RAM
  2. Xóa `.bss` về 0
  3. Gọi `SystemInit()`
  4. Gọi `main()` — nếu `main()` trả về thì treo trong vòng lặp vô hạn
- `HardFault_Handler` riêng, dừng tại chỗ bằng breakpoint để debugger bắt được

### 5. Application — `main.c`

- Bật clock cho GPIOC
- Cấu hình **PC13** output push-pull, tốc độ 2 MHz
- Nhấp nháy LED bằng vòng lặp busy-wait, chu kỳ khoảng 1 giây (chưa cần chính xác — timing thật là việc của BCM-002)
- Khai báo thêm hai biến toàn cục để chứng minh startup chạy đúng:

```c
uint32_t g_initialized = 0xDEADBEEFu;   /* phải nằm trong .data */
uint32_t g_zeroed;                       /* phải nằm trong .bss  */
```

### 6. Build targets

- Post-build tự động: sinh `.bin`, `.hex`, in kích thước bằng `arm-none-eabi-size`
- Custom target `flash`: `cmake --build build --target flash` → nạp firmware qua pyOCD

## Câu hỏi review

Trả lời bằng lời của bạn. Câu nào có chữ **thử** thì phải làm thật rồi mới trả lời.

1. Tại sao phần tử đầu tiên của vector table là một **giá trị stack pointer** chứ không phải địa chỉ hàm? Nếu giá trị đó sai thì chuyện gì xảy ra ngay sau reset?

2. `.data` có hai địa chỉ, VMA và LMA. Giải thích vì sao. **Thử** comment bước copy `.data` trong `Reset_Handler`, đọc lại `g_initialized` bằng gdb — bạn thấy giá trị gì, và vì sao lại là giá trị đó?

3. **Thử** bỏ `volatile` khỏi biến đếm trong vòng delay và build với `-O2`. LED làm gì? Mở `arm-none-eabi-objdump -d` ra, chỉ ra đoạn assembly giải thích hiện tượng.

4. Vì sao `--gc-sections` cần đi cùng `-ffunction-sections`? Vector table không được ai gọi tới — tại sao nó không bị linker xóa mất, và bạn đã chặn chuyện đó bằng cách nào?

5. Nếu quên bật clock GPIOC trước khi ghi vào thanh ghi cấu hình thì chuyện gì xảy ra? **Thử** rồi mô tả.

6. `nosys.specs` làm gì? Điều gì sẽ xảy ra khi link nếu gọi `printf` mà không có nó?

## Bẫy thường gặp

- **CMake báo compiler không hoạt động** ngay ở bước configure. CMake mặc định thử link một chương trình mẫu, mà bare-metal thì không link được nếu thiếu linker script. Tìm hiểu `CMAKE_TRY_COMPILE_TARGET_TYPE`.

- **GPIO của dòng F1 khác hoàn toàn các dòng STM32 khác.** F1 dùng `CRL` / `CRH`, mỗi chân 4 bit (MODE + CNF). Các dòng F4, G4, L4 dùng `MODER`, `OTYPER`, `OSPEEDR`. Tutorial trên mạng phần lớn viết cho F4 — copy sang là sai mà không báo lỗi gì.

- **LED trên PC13 là active-low.** Ghi 0 thì sáng, ghi 1 thì tắt.

- **PC13 là chân yếu.** Nó nằm trong vùng backup domain, chỉ chịu được dòng rất nhỏ và tốc độ tối đa 2 MHz. Đọc ghi chú về PC13–PC15 trong datasheet trước khi định cắm thêm tải vào đó.

- **Vector table bị linker xóa** → board không chạy, không có dấu hiệu gì. Liên quan câu hỏi 4.

- **Chip nhái trên Blue Pill.** Nhiều board dùng CKS32 hoặc chip không rõ nguồn gốc. Nếu pyOCD báo IDCODE lạ hoặc dung lượng flash không khớp 64K, dừng lại và báo tôi.
